## How I Think About Systems

### Design for failure

Networks fail. APIs time out. Messages arrive twice. Workers crash.

Failure handling should be part of the architecture rather than an afterthought.

### Make state explicit

Business workflows become easier to reason about when states, transitions, invariants, and ownership are visible in the model.

### Prefer correctness over cleverness

Especially in financial and distributed systems, predictable behavior and traceability are more valuable than unnecessary abstraction.

### Separate orchestration from execution

Long-running workflows, integrations, and distributed operations benefit from explicit coordination boundaries.

### Build for operability

A system is not finished when it works locally.

Logging, metrics, tracing, deployment, recovery, and debugging are part of the system.

### Keep architecture proportional

Start simple. Introduce complexity when the domain, scale, reliability requirements, or organizational boundaries justify it.

---

## Engineering Principles

```text
Correctness      > cleverness
Explicit state   > hidden behavior
Idempotency      > optimistic assumptions
Observability    > debugging by accident
Simple systems   > unnecessary abstraction
Evolution        > premature optimization
```
